Part one

In plain language

No technical background needed. Safe to read aloud to anyone.

The short answer

The one-sentence version

It watches for floods happening right now, works out how many people are inside the flood zone, drafts a prioritised list of what relief teams should do — and then hands that draft to a human, who approves, edits, or rejects it.

The draft is never acted on automatically. Nothing in the system dispatches supplies, sends a message, or moves a resource. Approving a recommendation records a decision, and that is all it does.

Motivation

The problem it solves

Disaster-response coordination is still largely manual. When a flood is unfolding, a coordinator has a satellite-imagery site open in one tab, a global alert feed in another, a population-density map in a third, and a spreadsheet in a fourth. They cross-reference by eye, under time pressure, and make a judgment call.

The data-gathering part of that is tedious and mechanical — a computer should do it. The judgment call is consequential and contested — a person should make it. This project splits the work along exactly that line: automate the tedious ninety percent, and put the consequential ten percent behind a human approval gate.

That split is the whole point. It is also the same tension real humanitarian-technology teams wrestle with, which is why the system is built to make the gate impossible to skip rather than merely discouraged.

Worked example

A real run, start to finish

This is an actual run against live data — an Orange-level flood alert in China, taken with the settings the system ships with: a five-day lookback, capped at the ten most urgent events. It took a few seconds. Read it as the story of what the system does.

ALERT MONITOR Queried GDACS for flood events, last 5 days, [Orange, Red] Found 1 event above threshold Selected event 1104081 (China, Orange) IMAGERY Affected-area polygon -> bbox 97.35, 26.05 -> 108.54, 34.31 (45.76 deg²) CMR-STAC: 10 granules of MCDWD_L3_F3_NRT_6.1 (28 matched) Map layer MODIS_Combined_Flood_3-Day @ 2026-08-19 POPULATION 79,946,082 people inside the flood polygon (658,855 pixels summed, 49 no-data skipped, WorldPop 2020 1 km) ALLOCATION Drafted 3 recommended actions from 4 candidate claims FACT-CHECK Verified 4/4 claims against 5 tool calls HUMAN GATE *** RUN PAUSED — waiting for a person *** Human approved by responder ACTION LOG Logged outcome: approved · 3 actions

Three things in that log are worth pointing at, because they are the design showing through:

  • "Found 1 event" is a real answer, not a thin one. Two filters produce it, both deliberate. The five-day window is short because GDACS keeps events listed for weeks after their window closes, so a wide lookback buries what is happening now. And the default alert levels are Red and Orange — GDACS rated 28 of the 29 floods active in this window Green, meaning minor or localized. The reviewer can toggle Green on; the system does not pad the list to look busier than the data is.
  • Every number carries its own receipt. "79,946,082 people" is not a figure the system asserts; it is the sum of 658,855 population-raster pixels inside the actual flood polygon, and the recommendation cites the exact data call — one of five logged in this run — that produced it.
  • The run genuinely stopped. Not "waited politely" — the process suspended and saved itself to a database. Had the server been restarted at that moment, the pending decision would still have been there afterwards.

What a failure looks like

This run found imagery. When it doesn't — NASA's near-real-time archive is only days deep, so a query for an older event legitimately returns nothing — the trace records ! No granules in the near-real-time window and falls back to a documented map-tile layer. It does not invent an image or quietly substitute a different date, and the gap becomes a caveat on the recommendation.

The core idea

The two rules that define it

1. A human always decides

The system drafts; it never acts. The pipeline reaches a point where it physically cannot continue on its own, and it waits there. A person then does one of three things — approve the draft as written, edit the actions and approve their version, or reject it — and whichever they choose is written to a log alongside who they were, when, and why.

Worth saying out loud

Approval records a decision. It does not dispatch anything. The output of this system is a reviewed document that a human then hands to whoever actually moves resources.

2. Every number must be traceable, or it doesn't ship

The known failure of language models in this setting is that they produce a confident, plausible, completely invented number. In disaster response, a figure that is off by a factor of two mis-sizes a relief operation.

So the system does not ask the model to be accurate. Between the drafting stage and the human, there is a checking stage — ordinary code, no AI — that goes through every number in the draft and asks: which data call produced this? Did that call succeed? Does this number actually appear in its result? Any number that fails is stripped out. If the number was load-bearing, the whole draft is blocked and never reaches a person at all.

A recommendation with a hole in it is worse than no recommendation.

In plain terms

Think of a newsroom fact-checker who cannot be talked round. The writer submits a story; the checker holds every figure against the source documents and deletes anything unsupported. The checker is not smarter than the writer — it just isn't guessing.

Scope

What it deliberately doesn't do

Being clear about the boundary is part of explaining the project honestly:

  • It doesn't dispatch, order, or send anything. There is no integration with a logistics system, and that is a design decision rather than an unfinished feature.
  • It doesn't estimate around missing data. If a population raster is unavailable, no population figure is produced — not an approximation, not last year's number. The gap is reported with its reason.
  • It doesn't forecast. It describes floods that alert agencies say are happening now; it does not predict where one will happen next.
  • It doesn't replace local knowledge. A satellite footprint and a population raster say nothing about which road is passable or which warehouse is stocked. That is precisely the knowledge the human at the gate brings.

Part two

How it works

The engineering, and the reasoning behind each choice.

Architecture

The pipeline, stage by stage

Seven stages, run as a state machine (LangGraph). Each stage receives the accumulated state, does one job, and appends to a shared trace that the dashboard streams live. The tag on each stage says what actually performs the work.

  1. 01

    Alert Monitor codellm tie-break

    Lists active GDACS flood events above an alert threshold — by default the last five days at the alert levels the reviewer has selected, capped at the ten most urgent. The cap is applied after ranking by alert level and recency, so it cuts the tail rather than dropping a Red event that GDACS happened to list late, and a truncated list reports how many matched. If several events are active, the model picks which is most urgent and says why — but its pick is validated against the candidate list, and the deterministic ranking is both the fallback and the check.

  2. 02

    Imagery Retrieval code

    Resolves the real affected-area polygon, derives its bounding box and area, searches NASA CMR-STAC for flood granules covering it, and builds a NASA GIBS tile layer for the map. The tile layer needs no network call, which is why it can back up the granule search when that comes back empty.

  3. 03

    Population Overlay code

    Sums WorldPop UN-adjusted population raster values inside the flood polygon — not inside the bounding box, and not a country total scaled down. Reports which countries were covered and which rasters were missing.

  4. 04

    Allocation Draft llm judgment

    Writes the headline, situation summary, prioritised actions, and caveats. It may only cite claim ids built from tool results it was actually given, and each action records which claims support it.

  5. 05

    Fact-Check deterministic code

    Verifies every claim against the tool-call log, strips what it cannot verify, and blocks the draft entirely if a load-bearing figure fails. Never a prompt — see below.

  6. 06

    Supervisor code

    Only runs when the fact-check blocked the draft. It names the rejected claims and their verbatim reasons, lists the only claim ids that may be cited, and sends it back to be redrafted. It stops on a spent attempt budget or on stagnation — a redraft rejected for the same claims as the attempt before it — so the loop cannot spin. A draft that never passes still never reaches a human.

  7. 07

    Human Gate a person

    Calls LangGraph's interrupt(). The graph suspends, the state is written to the checkpoint database, and nothing continues until someone resumes the run with a decision: approve, edit, or reject.

    The run stops here. This is not a pause — the process is gone.

  8. 08

    Action Log code

    Records the outcome — decision, reviewer, timestamp, notes, and the final action list including any edits. A draft blocked at stage five arrives here directly, so a blocked run is logged as such rather than vanishing.

Three of the routes between stages are conditional, and all of them fail toward telling the truth: if the Alert Monitor finds no event, the run skips to the log rather than fabricating one; if the Fact-Check fails, the run goes to the supervisor rather than to the human; and if the supervisor gives up, it goes to the log — never to the gate.

Where this came from

The supervisor is adapted from the supervisor component of NVIDIA's AVO architecture, which pairs an agent loop with a monitor that watches for "stagnation or repeated unproductive cycles" and redirects. Only that one component was adopted, and only here, because this is the single place in the pipeline with a real fitness signal to iterate against: the Fact-Check is a deterministic pass/fail oracle. The data-gathering stages keep their fixed call sequence — there is no search problem there to explore, so an exploratory loop would add latency and a fabrication surface for nothing.

Design decision

Where the AI is — and where it deliberately isn't

Only two of the seven stages use a language model, and that is the interesting part of the design. Extent, then population, then imagery is a fixed, correct sequence of calls. Handing that to a model would add latency, add cost, and add a surface where coordinates can be fabricated — in exchange for nothing, because there is no judgment in "call the next obvious tool".

The model is reserved for the two places that genuinely require judgment: choosing which of several active emergencies is most urgent, and writing a prioritised recommendation from evidence. Verification is deliberately excluded from that list.

Geometry never crosses the model boundary

A GDACS affected-area polygon is about 880 KB of coordinates. Passing it through a model would swamp the context window and invite it to truncate or invent coordinates. So tools are addressed by event id, and geometry is resolved server-side: the model names an event, but never handles spatial data. The polygon also never enters the checkpoint or the browser stream.

Three interchangeable engines

The same interface serves Anthropic directly, OpenRouter as a gateway to other models, and a rule-based path with no model at all.

The rule-based path is load-bearing, not a stub: it produces the same structured objects from the same tool results, so the entire pipeline — fact-check and approval gate included — runs and is testable with no credentials. Every recommendation records which engine drafted it, and the dashboard shows that. When the gateway is in use, the engine is read from the response rather than from the request, because OpenRouter may route to a different upstream than the one asked for — and in a system built on traceability, "which model wrote this" should not be a guess.

The important part

The guardrail

If someone only has time to look at one file, it should be backend/app/agents/factcheck.py. Three rules, enforced rather than requested:

  1. A numeric claim must cite a tool call from the current run.
  2. That call must have succeeded.
  3. The number must actually appear in that call's result.

And a fourth, following from the others: a source that was unavailable cannot be claimed about at all. If the population lookup failed, no population figure may be asserted — the recommendation states that the data is missing.

Why this is code and not a prompt

Asking a language model to verify another model's numbers reintroduces the exact failure the check exists to catch: a confident, plausible, unsourced figure. Verification here is lookup and arithmetic, and it is tested adversarially.

The test suite attacks it with the shapes a plausible-sounding fabrication actually takes:

Claim presented to the checkerVerdict
2,063,552 people, citing the real population callaccepted
~2.06M people — rounded, within 0.5% of the real figureaccepted
4,500,000 people, citing a real call that never produced that numberrejected
A number with no citation at allrejected
A number citing a call that doesn't existrejected
A number citing a call that failedrejected

The third row is the one that matters. Citing a genuine data call that simply never contained the quoted figure is the failure mode a human reviewer is least likely to catch by eye, and the one a model-based checker would most likely wave through.

Human-in-the-loop

The gate, and why runs survive a restart

The gate is a real suspension, not a loop that waits. LangGraph's interrupt() stops execution and hands the pending payload to whoever is driving the graph; the state is persisted by a checkpointer — SQLite locally, Postgres in the containerised stack.

The consequence is the feature: because the paused run lives in a database rather than in a process, a reviewer can close the tab, come back later, and still find the decision waiting. This was verified by restarting the backend container mid-approval and then approving the recovered run.

It also shapes the API, which is deliberately two endpoints rather than one long-lived connection:

GET /api/runs/{id}/stream streams the trace until the graph interrupts POST /api/runs/{id}/decision resumes the run with a human decision

Because the run is in the checkpoint, the stream can drop and the browser can close without losing the pending approval. Reconnecting replays the state instead of re-running the graph.

At the gate the reviewer can edit the actions, and editing is per-action by design: each action carries its own rationale and its own supporting citations through the edit, so rewording or removing one action cannot silently re-attribute another action's evidence.

Field notes

What the live data taught us

The data layer was built first and without any model involved — API quirks are far cheaper to debug that way, and every agent above inherits whatever the data layer gets wrong. Each finding below was discovered by probing the real APIs, is handled in code, and is pinned by a test so a regression to the naive version cannot pass.

TrapWhy it matters
WorldPop has two products; only the UN-adjusted one is correct here The unconstrained product overstates by a country-dependent margin — 38% for Nepal, 5% for Pakistan — enough to badly mis-scale a relief estimate
Population is a sum, not a mean Pixels hold people-per-pixel, so averaging understates a flood zone by orders of magnitude. No-data is -99999.0; a naive sum over Nepal returns -2.8e10
The GDACS event-list bounding box is a zero-area centroid Using it would compute population over a point. Real extents come from the geometry endpoint's affected-area polygon, so the event model deliberately exposes no bbox at all
Select by property, never by position GDACS returns the centroid and a much larger global polygon alongside the affected-area one, in undocumented order; CMR-STAC asset keys are production timestamps, so data assets are matched on file extension
NASA's near-real-time archive is only days deep Historical queries returning zero granules is correct, not a bug — so it is reported as unavailable and never backfilled from another date. GIBS tiles are the historical path
Two upstream defects worked around WorldPop's async statistics API never completes and leaks PHP warnings into its JSON; and the first file in a WorldPop record is not always a raster — Pakistan's is a zip archive

This table is the most persuasive part of the project to walk someone through, because none of it is guessable from documentation. It is what "verified against live APIs" actually means.

The dashboard

Three regions — an events rail, the map, and a tabbed detail panel — with the seven-stage pipeline across the top, driven live by the stream. The panel has four tabs: Brief (the recommendation, and the approve/edit/reject controls), Situation (measured figures with their provenance), Evidence (every claim and the tool call behind it), and Trace (the agents' reasoning, line by line).

The front end holds the same line as the backend: a missing value renders as an em dash, an unavailable source prints its reason, and a partial population total keeps its PARTIAL label and names the raster that is missing. No panel ever invents a value to fill a space.

Operations

Running it

The whole stack — Postgres, backend, dashboard — in one command:

docker compose up --build # then open http://localhost:3000

No key is required; without one the stack runs on the rule-based engine and every stage, including the gate, still works. To use Claude, copy .env.example to .env and set ANTHROPIC_API_KEY.

Or locally, without Docker — Python 3.12+ with uv, and Node 20+:

# terminal one cd backend uv sync --extra dev uv run uvicorn app.api:app --port 8088 --reload # terminal two cd frontend npm install npm run dev

There is also no-UI access, which is often the fastest way to show someone the data layer:

uv run python -m app.cli events --days 45 # live GDACS events uv run python -m app.cli report --event-id 1103933 # all sources + a provenance row per number uv run python -m app.cli cache # what's cached, by source

And the same five tools are served over MCP — python -m app.mcp_server over stdio, or --http — so any MCP client can call them directly.

Confidence

How it's tested

uv run pytest # 128 offline tests, no network uv run pytest -m live # 9 tests against the real APIs

The offline tests replay committed fixtures, and the fixtures are deliberately hostile — adversarial feature ordering, a zip archive listed before the raster, dynamic asset keys — so a regression to a naive implementation cannot pass them.

The nine live tests are the early-warning system for upstream API changes. Two of them are documentary: they will fail if GDACS or NASA improve their behaviour, which is the signal that a workaround can be deleted.

Status

Where it stands, and honest limits

Six phases are built and verified against live APIs: the data layer, the MCP tool surface, the agent graph, human-in-the-loop with checkpointing, the streaming console, and Docker Compose orchestration with Postgres.

Verified end to end in a real browser: pick an event, watch the trace stream, reach the gate, approve, and get the logged receipt — against live GDACS data, with a clean console.

Known gaps, stated plainly:

  • Historical replay mode is not built. It is the remaining planned feature, and the thing that would make demos independent of whatever is flooding today.
  • Two paths are verified only outside a browser — editing at the gate, and a draft blocked by the fact-check. Both are covered by tests against the real compiled graph; neither has been clicked through in a browser. The repair loop in particular is unreachable on the rule-based engine, which passes verification by construction.
  • One server process by design. The lock that stops two clients advancing the same run is process-local, so scaling out means moving that lock into Postgres first.
  • Population is a static annual raster. A 2020 raster against a 2026 event means exposure may have shifted — which is why the system emits that as a caveat on every recommendation rather than leaving the reader to remember it.

Part three

Explaining it to someone

Scripts and answers for when you're the one doing the talking.

Script

The 60-second pitch

Say it roughly like this. The order matters — problem, then split, then the guardrail, then the honest boundary.

Out loud

"When a flood is happening, a response coordinator has four browser tabs open — a global alert feed, satellite imagery, a population map, a spreadsheet — and they cross-reference by eye under time pressure.

This system does the cross-referencing. It pulls the live alert, works out the actual flood footprint, sums how many people are inside it, and drafts a prioritised list of what to do.

Then it stops. A human approves, edits, or rejects — and the run is genuinely suspended in a database until they do, so they can close the tab and come back.

The part I'd point at is the checking stage. Language models produce confident invented numbers, which in this domain mis-sizes a relief operation. So between the drafting and the human there's a stage of ordinary code that holds every number against the data call that produced it, and strips anything it can't verify. If a load-bearing number fails, the whole draft is blocked and never reaches a person.

And nothing is ever dispatched. Approving records a decision — the output is a reviewed document that a human hands onward."

Runbook

A five-minute demo

  1. Start with the events rail. "These are real flood events happening now, from the UN and EU joint alert system — last five days, ten most urgent." Then toggle Green on: the list jumps from one event to ten of twenty-nine. "Red and Orange are rare on purpose. Most active floods are Green — minor or localized — so the console defaults to the ones that warrant coordinating a response." Point out that a short list is a real answer, and an empty one is too.
  2. Click one, and narrate the stepper. The seven stages light up as the run advances. This is where the audience sees it is a pipeline, not a chatbot.
  3. Stop on any amber stage. If one appears — most often the imagery search finding nothing in the near-real-time window — that is the best moment in the demo: "it said so instead of substituting a different date. That's the whole design in one line."
  4. Land on the gate. The stepper shows the run halted and the Brief tab flags a decision waiting. Say plainly: the process is suspended in a database right now.
  5. Open the Evidence tab. Show a claim, its value, and the tool-call id beside it — then the tool-call log those ids point into, including any call that failed. This is the traceability claim made concrete.
  6. Approve, and read the receipt. "Approved and logged — and note what it says: this system does not execute response actions."

If you want the strongest single moment

Skip ahead to the fact-check table in Part two and walk through the third row — a number that cites a genuine data call which never contained it. Explaining why that one is rejected, and why a model-based checker would have let it through, lands harder than any screen in the app.

Anticipated

Questions you'll get

What stops the model from just making up a number?

Nothing stops it from drafting one — that's the realistic assumption. What stops it from reaching a person is the Fact-Check stage: deterministic code that requires every number to cite a successful tool call from this run and to actually appear in that call's result. Unverifiable claims are stripped; a load-bearing failure blocks the draft entirely.

Why not let the AI check its own work?

Because that reintroduces the exact failure being guarded against. A model asked to verify a plausible-looking figure will often agree with it. The check here is lookup and arithmetic, which cannot be persuaded.

Why not use an agent for everything, end to end?

Three of the stages have one correct call sequence. Delegating those to a model adds latency, cost, and a fabrication surface for no gain. The model is used where there is real judgment — triaging competing emergencies, and writing the recommendation.

Does it work without an API key?

Fully. With no credentials it runs the rule-based engine, which produces the same structured objects from the same evidence, so the fact-check and the approval gate are both exercised. Every recommendation records which engine drafted it, and the UI shows that.

What happens if a data source is down?

It is reported as unavailable with its reason, and nothing is estimated in its place. That gap becomes a caveat on the recommendation and is displayed in the console. A source that failed cannot be claimed about at all.

Is a human really required, or is it just the default?

Required. The graph calls interrupt() — execution stops and the state is persisted. There is no code path from drafting to a logged approval that does not pass through a submitted human decision.

How accurate is the population figure?

It is a sum of WorldPop UN-adjusted 1 km pixels inside the real flood polygon — so it is as accurate as that raster, and its year is stated. When a country's raster is missing, the total is labelled PARTIAL and names what's missing, because a partial total understates reality and must not be read as complete.

Could this be used for other disaster types?

The architecture transfers directly — the pipeline shape, the traceability rule, and the gate are hazard-agnostic. What is flood-specific is the source layer: GDACS event types, the MODIS flood products, and the extent geometry. Adding earthquakes would mean new source clients behind the same tool registry.

What was the hardest part?

Not the agents — the data. Every entry in the field-notes table was a wrong answer that looked right: the unconstrained population product, the centroid masquerading as a bounding box, averaging a raster that holds counts. Building the data layer first, with no model in the loop, is what made those findable.

Reference

Glossary

For anyone in the room who doesn't work with this vocabulary daily.

GDACS
Global Disaster Alert and Coordination System — a joint UN and European Commission service that publishes live disaster alerts with severity levels (Green, Orange, Red).
Affected-area polygon
The actual mapped shape of the flooded region, as opposed to a single point marking roughly where it is.
Bounding box
The smallest rectangle containing a shape. Cheap to work with, so it's what gets passed around — but population is summed over the real polygon, not the rectangle.
Raster
A grid of numbers laid over the map. In a population raster each cell holds how many people live in that square kilometre — which is why the correct operation over a flood zone is addition, not averaging.
Granule
One individual satellite data file covering a specific place and time.
Tile layer
Pre-rendered map imagery cut into small squares so a browser can fetch only the ones on screen. This is what the flood overlay on the map is made of.
UN-adjusted
A population product rescaled so national totals match official UN figures. The unadjusted alternative can be significantly high, which is why this one is mandatory here.
Provenance
The record of where a value came from: which source, which exact request, and when. Attached to every number this system produces.
Tool call
One request the system made for data, logged with its arguments, result, and outcome. The receipts the fact-checker verifies claims against.
Checkpoint
A saved snapshot of a run's state in a database. It's what lets a paused run outlive the server process.
Human-in-the-loop
A system deliberately built so it cannot complete a consequential step without a person's decision.
SSE
Server-Sent Events — a one-way stream from server to browser. How the trace appears line by line as the agents work, instead of all at once at the end.
MCP
Model Context Protocol — a standard way to expose tools to AI clients. The same five tools this system uses internally are served over it.
LangGraph
The library used to run the pipeline as a state machine, and the source of the interrupt that makes the human gate a real stop.
